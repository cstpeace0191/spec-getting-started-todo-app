# Research: Todo App Baseline

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

No `NEEDS CLARIFICATION` items remain. The decisions below follow from the clarified spec and
`requirements-KR.txt`.

## Decision 1: No authentication; one shared list

- **Decision**: All users share one task list. No sign-in, accounts, or per-user ownership.
- **Rationale**: FR-013 and constitution Principle I. The project scope is explicitly unauthenticated.
- **Alternatives considered**: Per-user lists with email/password (rejected: requires scope amendment,
  see the plan gate history in `spec.md` Clarifications). Third-party sign-in (same reason).

## Decision 2: Persistence chosen by environment variable

- **Decision**: Use MySQL when `MYSQL_HOST` is set; use SQLite (`SQLITE_DB_LOCATION`, default
  `/etc/todos/todo.db`) otherwise. Both sit behind `backend/src/persistence/`.
- **Rationale**: Matches `requirements-KR.txt` feature 6. Keeps local development simple (no database
  server) while supporting the containerized MySQL setup.
- **Alternatives considered**: MySQL only (rejected: needs a running server for every local run).
  SQLite only (rejected: the documented Compose setup uses MySQL 9.3).

## Decision 3: Item IDs generated by the server as UUID v4

- **Decision**: The backend creates the `id` for each new task, using UUID v4.
- **Rationale**: FR-007 requires IDs that never repeat. The server owns identity so clients cannot collide.
- **Alternatives considered**: Auto-increment integers (rejected: differ between MySQL and SQLite
  behavior and expose row counts). Client-generated IDs (rejected: trusts the client).

## Decision 4: Error state for failed loads is client-side

- **Decision**: When `GET /api/items` fails, the client shows an error message with a "Try again"
  button (FR-014). It does not show the empty-list message.
- **Rationale**: The API contract is unchanged; the behavior is a UI state. No new endpoint is needed.
- **Alternatives considered**: Server-side error page (rejected: the list is a client-rendered view).

## Decision 5: No maximum task name length

- **Decision**: The API and UI accept names of any length (FR-015).
- **Rationale**: Chosen in Clarification Q3. Note for implementation: SQLite and MySQL column types must
  not truncate names. Use an unbounded text type (for example, `TEXT`), not `VARCHAR(n)`.
- **Alternatives considered**: 100 or 255 character limits (rejected by the user).

## Decision 6: Performance target is 2 seconds

- **Decision**: The list appears within 2 seconds of opening the app under normal conditions (SC-004).
- **Rationale**: Chosen in Clarification Q4. A single list query with a small table meets this easily.
- **Alternatives considered**: 1 second (stricter, harder to verify) and 5 seconds (too slow for the
  user's expectation).
