## Phase 2: Foundational (Blocking Prerequisites)

**Purpose**: Persistence layer and server/client skeletons. No user story can start until this phase is complete.

**⚠️ CRITICAL**: Phases 3–7 depend on these tasks.

- [ ] T005 Create `backend/src/persistence/index.js`. Select MySQL when `process.env.MYSQL_HOST` is set, otherwise SQLite. Export one interface: `init()`, `getItems()`, `addItem(name)`, `updateItem(id, { name, completed })`, `deleteItem(id)`, `close()`. Data constraints from data-model.md: `id` is "UUID v4 string, generated by the server on create. Unique across all tasks. Never changes."; `completed` is "boolean, always `false` on create"; `name` is "text (unbounded)".
- [ ] T006 [P] Create `backend/src/persistence/sqlite.js`. Implement the interface from T005. Create table `todo_items (id TEXT PRIMARY KEY, name TEXT NOT NULL, completed INTEGER NOT NULL DEFAULT 0)` on init. Database path from `SQLITE_DB_LOCATION`, default `/etc/todos/todo.db`. Create the parent directory if it does not exist. Store `name` as unbounded `TEXT` (no `VARCHAR(n)`).
- [ ] T007 [P] Create `backend/src/persistence/mysql.js`. Implement the interface from T005. Wait for `MYSQL_HOST` to accept connections with `wait-port` before connecting. Read `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DB` (or their `*_FILE` variants). Create table `todo_items (id CHAR(36) PRIMARY KEY, name TEXT NOT NULL, completed BOOLEAN NOT NULL DEFAULT FALSE)` on init.
- [ ] T008 Create `backend/src/index.js`. Start an Express 5 app on port 3000. Call `persistence.init()` before listening. Mount all routes under `/api`. Serve the built client from `/static`.
- [ ] T009 [P] Create `client/index.html`, `client/vite.config.js` (dev server on port 5173, proxy `/api` to the backend), and `client/src/main.jsx` that renders `App`.
- [ ] T010 [P] Create `client/src/api/itemsApi.js` with `fetchItems()`, `addItem(name)`, `updateItem(id, { name, completed })`, `deleteItem(id)`. Each wraps `fetch` on `/api/items`. Each throws on any non-2xx response or network error, so callers can show the error state (FR-014) instead of treating failure as an empty list.

**Checkpoint**: Backend starts and connects to SQLite; client builds.

## Phase 3: User Story 1 - View and Add Tasks (Priority: P1) 🎯 MVP

**Goal**: The user sees the list (or the empty message, or the error state with "Try again") and adds a task.

**Independent Test**: Start with an empty store. Open the page; expect "No items yet! Add one above!". Add "Buy milk"; expect it in the list, unchecked, with an empty input.

- [ ] T011 [P] [US1] Create `backend/src/routes/getItems.js`. `GET /api/items` returns `200` with an array of `{ id, name, completed }` from `persistence.getItems()`. Empty store returns `[]`.
- [ ] T012 [P] [US1] Create `backend/src/routes/addItem.js`. `POST /api/items` takes body `{ name }`. Reject with `400` when `name` is missing or empty after trimming (data-model.md: "Non-empty after trimming whitespace (FR-005). No maximum length (FR-015)."). Generate `id` with the `uuid` package, v4. Store with `completed: false`. Respond with the created item.
- [ ] T013 [US1] Register the `getItems` and `addItem` routes in `backend/src/index.js` (after T008).
- [ ] T014 [P] [US1] Create `client/src/components/TodoListCard.jsx`. Call `fetchItems()` on mount. While loading, show "Loading...". On success with no items, show "No items yet! Add one above!". On success with items, render each item's `name` as text (US2 replaces this with `ItemDisplay`). On failure, show an error message with a "Try again" button that re-runs the fetch. Never show the empty message on failure (FR-014).
- [ ] T015 [P] [US1] Create `client/src/components/AddNewItemForm.jsx`. Text input and an "Add Item" button. Disable the button when the input is empty. While submitting, the button text is "Adding...". On success, clear the input and call a callback so the list can refresh.
- [ ] T016 [US1] Update `client/src/App.jsx` to render `AddNewItemForm` and `TodoListCard`. Pass a refresh callback from the form to the list.

## Phase 4: User Story 2 - Mark Tasks as Completed (Priority: P2)

**Goal**: The user toggles a task between completed and not completed.

**Independent Test**: Add a task, select its checkbox; expect the completed style. Select again; expect not completed.

- [ ] T017 [P] [US2] Create `backend/src/routes/updateItem.js`. `PUT /api/items/:id` takes body `{ name, completed }`, calls `persistence.updateItem`, returns the updated item. Return `404` if no task has that `id`.
- [ ] T018 [P] [US2] Create `client/src/components/ItemDisplay.jsx`. Show a checkbox icon (`faSquare` when not completed, `faCheckSquare` when completed, from `@fortawesome/fontawesome-free-regular`). Selecting it calls `updateItem` with `completed` inverted, then updates the item in place. Completed items get a `completed` CSS class.
- [ ] T019 [US2] Register `updateItem` in `backend/src/index.js`.
- [ ] T020 [US2] Update `client/src/components/TodoListCard.jsx` to render `ItemDisplay` for each item instead of plain text (depends on T014, T018).

## Phase 5: User Story 4 - Tasks Persist Between Visits (Priority: P2)

**Goal**: Changes survive a server restart.

**Independent Test**: Add a task and mark it completed. Stop and restart the backend. Reload; the task is still there with the same state.

- [ ] T021 [US4] In `backend/src/persistence/sqlite.js` and `backend/src/persistence/mysql.js`, make `addItem`, `updateItem`, and `deleteItem` resolve only after the write is committed, so a restart cannot lose an acknowledged change (FR-011).
- [ ] T022 [US4] In `backend/src/index.js`, handle `SIGINT`, `SIGTERM`, and `SIGUSR2`: call `persistence.close()` and then exit. This closes database connections cleanly on restart (requirements feature 7).

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies.
- **Foundational (Phase 2)**: Depends on Setup. Blocks all user stories.
- **User stories (Phases 3–7)**: Each depends on Foundational. US1 is the MVP. US2, US4, US3, US5 follow in priority order.
- **Polish (Phase 8)**: Depends on the stories being done.

### Story Dependencies

- **US1 (P1)**: Needs Foundational only.
- **US2 (P2)**: Needs US1 (the list component, T014, and the form/app wiring, T016).
- **US4 (P2)**: Needs Foundational. Can run in parallel with US2 (different files).
- **US3 (P3)**: Needs US2 (`ItemDisplay`, T018, and `TodoListCard`, T020).
- **US5 (P3)**: Needs Foundational. Can run in parallel with other stories (different files).

### Shared-File Note

`backend/src/index.js` and `client/src/components/TodoListCard.jsx` are edited by several tasks. Those tasks
are not marked `[P]` and must run one at a time.
